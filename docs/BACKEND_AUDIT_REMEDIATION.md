# Backend remediation — Eclipse-first baseline

## Consolidated behavior

1. **One upload policy source.** `UploadPurpose` is the single enum used to select the Cloudinary folder and decide allowed media types. Every managed URL must use HTTPS, `res.cloudinary.com`, the exact `cloudinary.cloud-name` configured for this application, an `aloute/` folder and the original URL recorded in the lifecycle ledger. URLs from another Cloudinary account, HTTP URLs, query/fragment URLs, encoded path separators, transformed URLs that differ from the registered original, purpose mismatches, untracked assets and a different uploader are rejected.
2. **No raw/document uploads without a scanner.** Both `UploadController` and `ImageStorageService` reject `DetectedType.FILE`; chat accepts only purpose-bound images/videos. The URL parser can still identify legacy `raw` assets for cleanup, but no active upload path creates new raw assets.
3. **Purpose-aware moderation.** `purpose=post` uploads are registered without making a remote moderation request on the upload thread; the post worker moderates the post text/media once after persistence. Chat/community/avatar/general image/video uploads are checked before their URL is returned when moderation is enabled. Upload-time remote media timeout is bounded by `MODERATION_UPLOAD_MEDIA_TIMEOUT` (default 12 seconds, capped in code). A disabled or unavailable moderation service is fail-closed for non-post public media.
4. **Redis upload rate limit.** Generic image/media routes and the direct user-avatar route apply the same per-user Redis bucket (30 uploads/hour; a 15-minute block after the limit). `RATE_LIMIT_REDIS_REQUIRED=true` fails closed when Redis is down instead of silently bypassing the security limit. Keep Redis bound to loopback for local development unless a secured deployment is configured.
5. **Single media lifecycle owner.** `MediaAssetLifecycleService` owns upload registration, uploader/purpose checks, attachment, rejected-upload cleanup, orphan cleanup, deletion requests, retries and tombstones. No controller or moderation wrapper deletes Cloudinary media directly. The legacy logical collection name `post_media_assets` is retained as a collection key inside the PostgreSQL JSONB document store. Ledger records include uploader, purpose and `postId` metadata where available. Exact URL references are checked in PostgreSQL using indexed JSONB fields and targeted revision-array predicates.
6. **Cleanup at all removal points.** Post, account and community deletion remove dependent comments, reactions, likes, reposts, saves, revisions, reports and notification outbox records. Post/chat removal writes durable media tombstones in the same PostgreSQL transaction as the owning JSONB document removal. Community deletion writes a PostgreSQL outbox job in the same SQL transaction, then a ShedLock-protected retry worker removes JSONB content in bounded batches and queues media cleanup. Replacing avatars/community images also calls the lifecycle owner. Cloudinary failures remain `DELETE_PENDING` for retry.
7. **No broken APPROVE after HIDE.** Moderation updates compare both the post id and previous moderation state, so concurrent APPROVE/HIDE actions cannot silently overwrite one another. HIDE queues current and revision media and records `mediaCleanupQueuedAt`; a scheduled reconciliation scan retries hidden posts whose queueing was interrupted. APPROVE rejects managed assets already marked `DELETE_PENDING` or `DELETED`, requiring replacement media and a new post.
8. **Moderation worker resilience.** Executor rejection rolls back the task's claim, lease and attempt count for both posts and comments, so an overloaded queue cannot consume retry budget or incorrectly push content to `FLAGGED`. Scanner claim size is bounded against the configured executor capacity. HTTP moderation calls occur outside database transactions; persistence work remains short and retryable. Direct cache eviction failures are logged and left to TTL expiry.
9. **Cache vs rate-limit outage policy.** Redis cache errors are logged and fail open because cache is only an optimization, including explicit moderation cache eviction. Authentication and upload rate limits remain separate: production defaults `RATE_LIMIT_REDIS_REQUIRED=true` and returns 503 when Redis is unavailable, while local development uses a per-instance fallback that still enforces the limit. WebSocket presence uses Redis per-session leases; on Redis outage only same-node presence is temporarily available.
10. **Build and docs.** `pom.xml` uses Spring Boot 4.1.1 and Java 21, enables Maven Failsafe for PostgreSQL/Flyway/Hibernate fresh-schema validation, and keeps the migration policy and current source manifest under `docs/`. PostgreSQL schema changes extend through `V20261109` in the merged checkout; `V20261106` owns the temporal-key JSONB expression indexes and the later `V20261109` compatibility helpers are retained for the user database already migrated in the previous session.
11. **Multi-replica runtime.** Docker Compose now provisions Coturn, RabbitMQ/STOMP relay, Redis-backed presence/rate limits/call state, a PostgreSQL-backed JSONB document store, two application replicas and Nginx. Production still has to provide a public TURN address, TLS termination and externally managed database/backup credentials appropriate to the target environment.
12. **Pagination and account administration.** Community join requests and user/post search expose bounded `page`/`size` parameters and the browser UI can load subsequent pages. HOST growth charts use PostgreSQL daily aggregation with a short cache instead of loading every timestamp into Java. Unknown routes require authentication. Access-token denylisting is mandatory in both logout and JWT validation. ADMIN account APIs provide paginated search, lock/unlock, forced logout and an immutable reason/history audit trail.

## Validation status

The Java 21 source compiles and the complete Maven unit-test suite is run after each remediation batch. `mvn verify` also exercises Failsafe; the fresh-schema integration test executes only when its disposable PostgreSQL connection variables are supplied. Real OpenAI moderation, Cloudinary deletion and multi-network WebRTC/TURN still require test credentials and infrastructure. Useful release checks are:

```powershell
.\mvnw.cmd clean test
.\mvnw.cmd verify
.\deploy\scripts\validate-empty-schema.ps1
```

The schema validation script uses disposable local PostgreSQL and must not be pointed at Supabase or another shared database. Use test accounts and test Cloudinary assets for lifecycle verification.
