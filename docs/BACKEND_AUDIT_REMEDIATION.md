# Backend remediation — Eclipse-first baseline

## Consolidated behavior

1. **One upload policy source.** `UploadPurpose` is the single enum used to select the Cloudinary folder and decide allowed media types. Every managed URL must use HTTPS, `res.cloudinary.com`, the exact `cloudinary.cloud-name` configured for this application, an `aloute/` folder and the original URL recorded in the lifecycle ledger. URLs from another Cloudinary account, HTTP URLs, query/fragment URLs, encoded path separators, transformed URLs that differ from the registered original, purpose mismatches, untracked assets and a different uploader are rejected.
2. **No raw/document uploads without a scanner.** Both `UploadController` and `ImageStorageService` reject `DetectedType.FILE`; chat accepts only purpose-bound images/videos. The URL parser can still identify legacy `raw` assets for cleanup, but no active upload path creates new raw assets.
3. **Purpose-aware moderation.** `purpose=post` uploads are registered without making a remote moderation request on the upload thread; the post worker moderates the post text/media once after persistence. Chat/community/avatar/general image/video uploads are checked before their URL is returned when moderation is enabled. Upload-time remote media timeout is bounded by `MODERATION_UPLOAD_MEDIA_TIMEOUT` (default 12 seconds, capped in code). A disabled or unavailable moderation service is fail-closed for non-post public media.
4. **Redis upload rate limit.** Generic image/media routes and the direct user-avatar route apply the same per-user Redis bucket (30 uploads/hour; a 15-minute block after the limit). `RATE_LIMIT_REDIS_REQUIRED=true` fails closed when Redis is down instead of silently bypassing the security limit. Keep Redis bound to loopback for local development unless a secured deployment is configured.
5. **Single media lifecycle owner.** `MediaAssetLifecycleService` owns upload registration, uploader/purpose checks, attachment, orphan cleanup, deletion requests, retries and tombstones. The legacy Mongo collection name `post_media_assets` is retained to read records created by earlier versions. Ledger records include uploader, purpose and `postId` metadata where available. The cleaner scans only old `UPLOADED` assets and `DELETE_PENDING` deletions; `ATTACHED` assets are not repeatedly re-scanned. Mongo exact URL matching uses indexed fields instead of broad unanchored regular expressions.
6. **Cleanup at all removal points.** Hiding/deleting posts queues current and edit-history media for deletion only if no other active reference remains. Replacing avatars/community images, leaving a community as the last member, deleting a community, deleting an account, and deleting a chat message for everyone call through the same lifecycle service. Uploads left unattached in chat/community/avatar flows remain `UPLOADED` and are reclaimed after the orphan grace period. Cloudinary invalidation is requested during destroy; deletion failures remain `DELETE_PENDING` for retry.
7. **No broken APPROVE after HIDE.** If a post's managed asset is `DELETE_PENDING` or `DELETED`, a later admin `APPROVE` is rejected with a message requiring the author to upload replacement media and submit a new post. Tombstones are retained while a post/history still refers to the URL and are pruned only after the retention period and reference checks.
8. **Moderation worker resilience.** Executor rejection rolls back the task's claim/lease/attempt count so an overloaded queue cannot increment retries or incorrectly push a post to `FLAGGED`. Scanner claim size is bounded against the configured executor capacity. HTTP moderation calls occur outside Mongo transactions; the transaction is limited to the result update/counter writes.
9. **Cache vs rate-limit outage policy.** Redis cache errors are logged and fail open because cache is only an optimization. Authentication/upload rate limiting remains governed separately by `RATE_LIMIT_REDIS_REQUIRED`. WebSocket presence uses Redis per-session leases refreshed by the current application node. `PRESENCE_REFRESH_INTERVAL_MS` must be positive and less than half the effective session lease to avoid false offline transitions; on Redis outage only same-node presence is available temporarily.
10. **Build and docs.** `pom.xml` uses the requested Spring Boot 4.1.1 / Java 21 / `jackson-2-bom.version=2.21.7` dependency set, enables Maven Failsafe for the fresh PostgreSQL/Flyway/Hibernate validation test, and keeps a single canonical migration document at `docs/DATABASE_MIGRATIONS.md`. `docs/PATCH_MANIFEST.txt` is the one canonical file list.
11. **Known infrastructure TODO.** Backend TURN REST credentials can be generated when TURN is configured, but this source does not provision a real TURN/Coturn server. STUN-only calls may fail on restrictive NAT. Redis presence state is shared, but cross-instance STOMP broadcast still needs RabbitMQ/relay deployment. These deployment items are intentionally left for the group's Docker phase.

## Validation status

Static checks were performed on the archive/source: POM XML parsing, YAML parsing, JavaScript syntax checks, Python AST checks, references to removed lifecycle classes/methods, and ZIP integrity. A successful Java compile, complete Maven unit-test run, fresh-schema integration run, real OpenAI moderation run, Cloudinary deletion test, or multi-network WebRTC/TURN test must not be inferred from those static checks. Run the commands below on the developer machine:

```powershell
.\mvnw.cmd clean test
.\mvnw.cmd verify
.\deploy\scripts\validate-empty-schema.ps1
```

The schema validation script uses disposable local PostgreSQL and must not be pointed at Supabase or another shared database. Use test accounts and test Cloudinary assets for lifecycle verification.
